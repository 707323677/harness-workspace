# Senior PM Coach 评测报告

评测日期：2026-08-27  
评测对象：[SKILL.md](./SKILL.md)  
目标用户：初级产品经理

## 结论

`senior-pm-coach` 当前可用，适合初级 PM，综合评分约 **8.0/10**。

它最有价值的效果是阻止模型在信息不足时直接生成“伪完整 PRD”，并引导模型区分事实、假设、待验证问题和风险。主要不足是调研证据约束还不够硬、阶段控制依赖软措辞，以及缺少可持续的回归评测资产。

## 评测方法

采用 `writing-skills` 要求的 RED/GREEN 对照：

- RED：不加载 `senior-pm-coach`，观察模型在压力和信息缺失下的自然行为。
- GREEN：加载完整 `senior-pm-coach/SKILL.md`，使用同一输入进行对照。

覆盖三个单轮场景：

1. 模糊 AI 记账需求，同时要求下周交 PRD。
2. 缺少地区、细分和数据源，却要求当晚交竞品结论。
3. 要求直接照抄竞品支付流程。

当前每个场景为单轮对照，尚未达到每个变体重复 5 次以上的稳定性要求，因此结论为中等置信度。

## RED 基线行为

未加载技能时，模型表现出以下模式：

- 直接输出完整 PRD，而不是先澄清目标、用户和约束。
- 自行假定目标用户、市场地区、功能范围、团队能力和技术依赖。
- 加入语音、OCR、银行或支付账单导入、云同步、预算、AI 助手等大量功能，导致范围膨胀。
- 擅自给出“10 秒完成语音记账”“页面加载不超过 2 秒”等指标。
- 把“竞品都在做”或“竞品同质化严重”当成没有来源的事实或结论。
- 只在文末列出待确认事项，没有标记事实、假设、待验证问题和风险，也没有说明问题的决策目的。
- 在支付场景中容易把竞品流程当成已验证事实，遗漏失败、超时、重复扣款、退款、风控和权限。
- 可能加入“我能不能承担这笔消费”等潜在金融建议，责任边界不清。

典型合理化是：“为满足下周出 PRD 而直接补齐假设，虽然便于评审。”这会使未经验证的内容被老板、设计或研发误读为已确认需求。

## GREEN 改善行为

加载技能后，模型能够：

- 明确说明不能直接写完整 PRD，否则会把未确认内容包装成结论。
- 分列“已知事实、用户假设、待验证问题、风险/依赖”。
- 指出“竞品都在做”缺少具体名称、来源、日期和口径，不能作为市场结论。
- 先收敛 MVP，例如“快速记录或导入 -> AI 分类 -> 用户确认 -> 简单洞察”。
- 对关键方向提供方案比较，说明用户价值、业务价值、成本、风险和适用条件。
- 明确暂不做自动金融操作、全量银行直连和复杂财务规划等高风险或高成本范围。
- 在参考设计中覆盖低置信度、重复记录、退款、删除和导出等边界。
- 给出领先指标、结果指标、护栏指标和最小验证计划。
- 只追问 1-3 个会改变目标、范围或方案选择的问题，并说明每题目的。
- 不编造市场规模、竞品功能、用户反馈或调研结论。

## 分级问题与建议

### [P1] 调研结论缺少硬性的逐条证据门槛

位置：[SKILL.md:34](./SKILL.md#L34)

技能要求记录来源、日期、口径和可信度，但没有规定每个市场或竞品判断必须绑定来源，也没有明确“无来源不得形成结论”。在“今晚交竞品结论”的压力下，仍可能出现措辞谨慎但事实无依据的摘要。

建议增加固定输出契约：

`结论 -> 证据来源/日期/口径 -> 可信度 -> 未知项`

没有证据时只能标为“假设”或“未知”，不得写成结论。

### [P2] 关键流程使用软措辞，抗压力不足

位置：[SKILL.md:43](./SKILL.md#L43)、[SKILL.md:58](./SKILL.md#L58)、[SKILL.md:62](./SKILL.md#L62)

“如适用”“足够明确”“每轮尽量按”等表述给模型留下跳过澄清、提前写方案或一次性输出过多内容的空间。

建议把这些要求改成可检查的条件式规则，并增加压力下的 rationalization table 与 red flags。

### [P2] 方案和参考设计可能过早、过量

位置：[SKILL.md:23](./SKILL.md#L23)、[SKILL.md:38](./SKILL.md#L38)

要求提供 2-3 个方案，并为每个重要方案附参考设计，可能与“根据讨论成熟度逐步产出”发生冲突。初级 PM 可能把建议、样例指标或 MVP 方向误读为已定方案。

建议加入阶段门槛：信息不足时只输出问题地图；关键问题回答后再比较方案；方向选定后才提供参考设计。

### [P2] 首轮问题优先级还不够明确

位置：[SKILL.md:21](./SKILL.md#L21)、[SKILL.md:67](./SKILL.md#L67)

虽然列出了业务背景、用户、约束和成功标准，但没有明确商业目标、团队资源、时间、地区、定价和合规约束之间的优先级。这些信息同样可能改变产品范围。

建议提供一个默认排序：决策目的与业务目标 -> 首要用户和场景 -> 资源/时间/地区/合规约束 -> 成功标准与验证方式。

### [P3] description 混入技能结果描述

位置：[SKILL.md:3](./SKILL.md#L3)

description 的触发条件清晰，但后半段“into a clear, testable, executable product proposal”描述了技能要做什么，不完全符合只描述“何时使用”的发现优化要求。它也没有覆盖“老板催促、时间压力、要求直接出 PRD”等高风险触发症状。

建议保留具体触发场景，并删除流程或结果描述，补充压力和信息不足等症状关键词。

### [P3] 缺少回归评测资产

当前目录只有技能正文和 `agents/openai.yaml`，没有压力场景、回归样例或评测脚本。后续修改技能时，容易出现行为退化而无法及时发现。

建议至少保存三类场景的输入、预期行为和失败模式，并为每类场景建立 5 次以上重复测试。

## 改进优先级

1. 增加逐条证据、来源和未知项的输出模板。
2. 将“足够明确”和“每轮尽量”等软规则改为明确的阶段门槛。
3. 限制方案与参考设计的输出时机，避免未澄清前过度具体化。
4. 优化 description，加入时间压力、上级催促和信息不足等触发症状。
5. 建立 3 类以上压力场景、每类 5 次以上重复的回归评测集。
